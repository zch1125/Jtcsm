## 问题 1：小程序 API 的 `/v3/api-docs` 返回 500

### 现象

- `GET http://localhost:8081/v3/api-docs` 返回 HTTP 500。
- 返回体为统一错误格式：`{"code":500,"message":"服务器内部错误","data":null}`。
- `GET http://localhost:8081/swagger-ui.html` 可以正常打开页面，但页面加载文档数据时会失败。

### 影响

- Knife4j / Swagger 接口文档无法使用。
- 前后端联调时无法直接通过接口文档确认参数。

### 复现方式

```powershell
curl.exe http://localhost:8081/v3/api-docs
```

### 已确认信息

- 根因：springdoc 2.3.0 在 Spring 6.2 下调用已移除的 `ControllerAdviceBean(Object)`；Knife4j 4.5.0 在 springdoc 升级后仍调用旧 API。
- 修复后依赖组合：springdoc-openapi-starter-webmvc-ui 2.8.4，移除 Knife4j starter。
- API 业务接口本身正常，`/api/v1/recipe/hot` 返回 200。

### 排查方向

1. 查看 API 进程日志中 springdoc 初始化或请求处理时的异常堆栈。
2. 检查是否存在无法被 OpenAPI 解析的 Controller 返回类型，例如 `Result<List<Map<String, Object>>>`、泛型嵌套等。
3. 检查是否由 Knife4j 与 springdoc 版本组合兼容性问题导致。
4. 可临时禁用 Knife4j（`knife4j.enable=false`）对比定位。

### 建议修复

- 优先根据真实异常堆栈定位，避免直接升级版本掩盖问题。
- 若为返回类型解析问题，将 `Map` 类型替换为明确 DTO。
- 若为版本兼容问题，统一升级 springdoc / Knife4j 到互相兼容的版本，并回归测试。

### 验收标准

- `curl.exe http://localhost:8081/v3/api-docs` 返回 200。
- Swagger UI 页面能正常展示接口列表。

## 问题 2：Elasticsearch 菜谱索引无数据，RAG 检索不可用

### 现象

- ES 中 `jtcsm_recipe` 索引已创建，但文档数为 0。
- `GET http://localhost:8081/api/v1/recipe/search?keyword=番茄` 返回 200，但结果为空。
- `jtcsm_knowledge_md` 索引未创建或未初始化。

### 复现方式

```powershell
curl.exe "http://localhost:9200/jtcsm_recipe/_count"
curl.exe "http://localhost:8081/api/v1/recipe/search?keyword=番茄"
```

### 已确认信息

- Elasticsearch 8.15 正常运行在 9200 端口。
- `RecipeIndexService` 已成功创建 `jtcsm_recipe` 索引，向量维度为 1024。
- 环境变量 `DEEPSEEK_API_KEY` 已配置。
- `EmbeddingService` 调用 embedding 失败后，`RecipeIndexService.syncBatch` 捕获异常并继续，最终没有写入文档。

### 可能原因

- DeepSeek 官方 API 不提供 `text-embedding-v3` embedding 接口，当前配置的 embedding 调用实际不可用。
- chat 与 embedding 共用 `https://api.deepseek.com`，未区分不同供应商的 base-url。
- `KnowledgeBaseMdService` 没有在启动时自动初始化 Markdown 知识库索引。

### 建议修复

1. 接入真正支持 embedding 的服务（如 OpenAI `text-embedding-3`、硅基流动、阿里百炼等）。
2. 在配置中把 chat 和 embedding 的 base-url、api-key、model 拆分，避免共用一套配置。
3. 启动完成后主动触发索引初始化：
   - `POST /api/v1/knowledge/init-md-index`
   - `POST /api/v1/knowledge/sync`
4. 检查 `syncBatch` 的失败日志，确认向量写入成功后再认为 RAG 可用。

### 验收标准

- `curl.exe "http://localhost:9200/jtcsm_recipe/_count"` 返回 `count > 0`。
- `jtcsm_knowledge_md` 索引存在且有文档。
- `/api/v1/recipe/search` 能返回菜谱结果。

## 问题 3：网关 `/admin-api/**` 路由与管理后台实际前缀不一致

### 现象

- 网关配置的路由为 `/admin-api/**`，转发到 `jtcsm-admin:8082`。
- 管理后台所有 Controller 的实际路径前缀是 `/api/admin/**`。
- 经网关访问管理后台 API 时无法命中实际接口。

### 复现方式

```powershell
curl.exe http://localhost:8080/admin-api/actuator/health
```

### 影响

- 网关作为统一入口时管理后台 API 不可用。
- 当前本地管理后台通过 Vite 代理 `/api/admin` 直连 8082，因此未暴露到业务路径，但生产网关/Nginx 配置存在不一致风险。

### 建议修复

- 推荐在网关中新增或修改为 `/api/admin/**` 路由，与 Nginx 的 `location /api/admin/` 保持一致。
- 或统一把管理后台 Controller 前缀改为 `/admin-api`。
- 同步检查 `AuthGlobalFilter` 的白名单前缀是否覆盖登录接口。

### 验收标准

- `curl.exe http://localhost:8080/api/admin/login` 能经网关转发到 8082。
- 网关白名单内路径不需要 token 也能放行。

## 问题 4：`jtcsm-api` 无法通过 `mvn spring-boot:run` 启动

### 现象

- 按 AGENTS.md 执行 `mvn spring-boot:run`（dev profile）后，Maven 打印 `BUILD SUCCESS`。
- 但 8081 端口没有监听，API 实际没有启动。

### 复现方式

```powershell
cd D:\Project\Jtcsm\backend\jtcsm-api
mvn spring-boot:run -Dspring-boot.run.profiles=dev
netstat -ano | findstr :8081
```

### 根因

`jtcsm-api/pom.xml` 中 `spring-boot-maven-plugin` 配置了：

```xml
<skip>true</skip>
```

该配置本意是跳过 repackage，保证 `jtcsm-api.jar` 是普通库 jar 供 `jtcsm-admin` 引用，但 `spring-boot:run` 同样受 `skip` 影响，导致直接运行被跳过。

### 影响

- 与项目启动文档不一致。
- 目前 API 需要绕道使用 `java -cp` 或类路径方式启动。

### 建议修复

1. 将 skip 配置限定到 `repackage` 目标，例如通过 `executions` 单独配置，或改为占位符 `-Dspring-boot.repackage.skip=true`。
2. 保证 `jtcsm-admin` 仍能引用普通 jar 的同时，`mvn spring-boot:run` 可以正常启动 API。
3. 修复后更新 AGENTS.md 或保留 dev 启动脚本，避免后续再次踩坑。

### 验收标准

```powershell
cd D:\Project\Jtcsm\backend\jtcsm-api
mvn spring-boot:run -Dspring-boot.run.profiles=dev
netstat -ano | findstr :8081
```

- 8081 端口正常监听。
- `curl.exe http://localhost:8081/api/v1/recipe/hot` 返回 200。
